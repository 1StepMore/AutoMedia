## 三、🎯 目标形态（这两个项目应该成为的样子）

> **这一章是最终目标图景（项目的"应该成为的样子"）。**
> **首个里程碑**：让采集端与生产端在这些形态的框架下**真跑通**（可对外演示的完整 demo）。
> **最终目标**：以下形态**全部达成**。coding agent 应据此形成自己的实现方案。

### 形态 A：门控的产出是「可交付的合规报告」

**应该成为的样子**：
- 门控跑完，产出的不是"通过/不通过"，而是**客户可直接使用/交付的报告**
- 报告要让**非技术客户**看懂三件事：**哪条不达标 / 为什么不达标（依据）/ 怎么改**
- 报告可以**直接交给第三方**（客户方、监管方、上级）而不需要额外解释
- 报告能体现"**达标度**"而不仅是"过没过"（客户要看趋势和改进）

### 形态 B：标准与实现分离

**应该成为的样子**：
- **标准是可配置的数据**，不是写死在代码里的逻辑
- 换一个客户 / 换一个行业，改的是**配置**，不是**代码**
- 引擎是通用的——**同一套引擎服务所有客户**，差异全部在标准层
- 标准能表达"为什么"（依据）和"怎么改"（修复指引），而不只是"规则本身"

### 形态 C：能连续无人值守运行

**应该成为的样子**：
- 从"能跑一次"到"**能连续跑、出错能定位、中途失败能断点恢复**"
- 任一环节失败不影响其他环节（隔离性）
- 有客观证据表明它能长时间稳定运行（而不是"理论上应该稳定"）

### 形态 D：客户能找到我们

**应该成为的样子**：
- 有可被搜索发现的内容资产（目标客户会搜的问题，我们能回答）
- 有**多语言分发能力**（这是我们的独有优势）
- 落地页能让人一句话说清我们做什么（不是"AI 内容工具"）

### 形态 E：有可展示的信任凭证

**应该成为的样子**：
- 有**前后对比案例**——同一篇内容，用系统前后的差异可量化展示
- 案例既是销售证据，也是"可交付报告"的自然延伸

## 三·补、本次 demo 的范围界定（2026-09-15 补充）

> **背景**：coding agent 核对代码后提出三个范围疑问。以下为发起人侧的界定，**优先于任何更宽的解读**。

### 界定 1：「合规/标准」= **通用内容质量**（本次 demo）

**本次 demo 采用现有门控所代表的通用内容质量标准，不实现「客户/行业自定义规则集」。**

- 第一章已定首个成果 = **采集端与生产端真跑通**；第三章形态 A–E 明确标注为"**最终目标：全部达成**"，是终局图景，**不是首个 demo 的验收项**
- 因此不存在"二选一"的冲突，**这是排序问题**：形态 B 的触发条件是「出现第二个客户 / 换行业」——那时才有真实差异需要表达。在拿到第一个真实客户前设计规则集，属于猜测性设计
- 亦不触及红线：现有门控不阻碍"demo 跑通"这一目标，不落入"阻碍赚钱"三条判据 → **本次不改动现有门控**

**现状事实（供核对，非方向指引）**：现有门控的检查项以函数形式写在 Gate 类内；同时代码中**已存在一条「品牌配置 → 门控」的数据通路**（`brand_profiles.yaml` → `GateContext.brand_profile` → 各 gate 读取，如 `G3BrandCTA` 读 `brand_name`/`aliases`/`blocked_words`/`cta_principles`）。**不存在**"行业/客户规则集"概念（无规则集加载器）；`brand_profile` 的 `industry` 字段仅作描述性上下文，不驱动任何门控判定。形态 B 是否等同于"重写架构"，**由 coding agent 实跑后自行判断**。

### 界定 2：「采集端」= **选题发现**（现有能力），不新建抓取子系统

**本次 demo 的采集端 = 选题发现（现有 `HotCollector`），不新建 RSS / 网页 / 社媒趋势抓取子系统。**

- 选题发现已是**真实调用外部信源**（真实外部搜索 API + 真实聚合/生成层），非 mock → 已满足"真跑通"
- 新建抓取子系统属**新能力**，其价值取决于客户要什么信源 → 同界定 1，留到有客户后定
- 待修项（内存态池子 / 落库 / 定时触发）属"让现有能力真跑通"，是 demo 范围内的**修**，不是新建

**现状事实（供核对，非方向指引）**：

- `HotCollector.collect_all()` = 关键词搜索层 + 聚合/生成层 + seed 话题 → 标题去重
- `HotCollector.ingest_file()` = 文档摄取（docx/pdf/pptx/xlsx/csv/json/xml/html/epub/eml/msg）
- `PoolDB` = SQLite，方法集完整（增删查改 / 评分 / 标记 / 简报挂载 / 计数）
- **`PoolDB(":memory:")` 出现于 `mcp/tools.py` 三处** → 走 MCP 路径时池子为内存态，不落盘
- `cron/jobs.yaml` 定义 4 个 job 模板（含 `depends_on` 链）；`automedia cron run <job>` 有真实实现
- **但 jobs.yaml 目前只被"校验"读取，无 scheduler 消费它定时触发** → 定时需外部调度器调用 CLI

### 界定 3：**视频显式排除在首个 demo 之外**

**视频不是本次 demo 的必要部分。**

- **AutoMedia 自身不含视频生产**：`pipelines/` 只有音频与图片两条，无视频 pipeline；视频渲染依赖**外部 CLI 工具** `hyperframes`
- **本机当前无该外部工具**（`which hyperframes` 为空）→ 视频模式实际跑不了
- **架构上视频本就是独立可选轨**：文本轨门控集**不含任何 V 门**；视频轨 V0–V7 独立成组。且外部工具缺失时，V 门**优雅降级为 skipped，不判失败**

→ 因此「视频链跑不通」的准确表述是「**外部渲染依赖未就绪**」，而非 AutoMedia 核心链断裂。把视频纳入 demo，会把工作量从"验证现有链"变成"部署调试外部渲染工具"，与第一章的 demo 定位不符。**首个 demo 以文本轨（+可选图片轨）为准。**
