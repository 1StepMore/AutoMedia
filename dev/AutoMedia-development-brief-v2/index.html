    AutoMedia 开发简报¶

    性质：方向简报（由首席助手基于最终发起人的 expectation 形成） 用途：交给 coding agent 核对代码现状 → 由其形成自己的开发方案 本简报不含实现路径——怎么实现由 coding agent 决定

    版本：v2（2026-09-15）— 相对 v1 的两处实质变更： ① 新增「三·补、本次 demo 的范围界定」（界定 1/2/3） ② §五 修正为两档（v1 把终局标准与 demo 标准混列，末条与界定 1 直接矛盾）

    权威路径：D:\Hermes-Workspace\00-Records\商业化评估-20260914\AutoMedia开发简报.md （全盘唯一副本；位于 Hermes-Workspace，不在 AutoMedia 仓库内，搜仓库找不到） ⚠️ 若你手上这份没有「三·补」、或 §五 未分档 → 那是 v1 旧版，请以本路径的磁盘版为准。

    零、商业定位（读懂这张卡即可，代码背景你已熟悉）¶

    项 内容
    卖什么 内容符合标准的保证能力（不是"帮你写内容"）
    卖给谁 有品牌标准、需要稳定产出的组织
    当前阶段 demo——采集端与生产端真跑通；不搞付费端等空中楼阁
    商业目标 赚钱（项目为现金流服务，非技术练习）
    与 AutoInfo 关系 共用部分技术底座，但商业逻辑不同（我们卖"生产能力"）；并行推进

    一、Expectation（最终发起人的期望，最高优先）¶

    终局形态¶

    内核（能力本身）+ 私有部署优先，兼容 SaaS 与服务：

    层 内容
    内核 可配置的标准 + 执行引擎（这是能力本体，不随交付方式变）
    外壳 1 私有部署（先做——兼容性最强、最快能签单）
    外壳 2 SaaS（有客户后加多租户/计费）
    外壳 3 服务（用同一内核帮客户做，无需产品化）

    首个成果¶

    能对外演示的完整 demo——采集端与生产端真跑通（不是概念演示，是实际运行的层级）。

    商业模式¶

    卖"内容符合标准"的保证能力，不是"帮你写内容"。

    目标客户（假设）¶

    品牌代理 / 内容团队——有品牌标准、需要稳定产出的组织。

    时间¶

    不设时间节点。持续开发，与 AutoInfo 并行推进。

    二、为什么（商业依据）¶

    事实 数据来源 含义
    "AI 写作工具"定位已死 Jasper 营收 $120M→$55M，估值 $1.5B→$55M ❌ 不做"帮你写"
    质量门控是空白 现有玩家只有企业级（Writer $30 万/年）或开源单体 ✅ 我们的位置
    无人串成完整流水线 没有一家把"采集→生成→强制质检→发布"做成默认流程 ✅ 我们的位置
    理论已被公开 Explorium 五门理论、CheckApp 开源 ⚠️ 窗口有限
    国内价格地板低 ¥57-99/月 → 出海优先
    企业级能收溢价 Writer NRR 160%、$30 万/年合同 ✅ 质量/一致性可定价

    三、🎯 目标形态（这两个项目应该成为的样子）¶

    这一章是最终目标图景（项目的"应该成为的样子"）。 首个里程碑：让采集端与生产端在这些形态的框架下真跑通（可对外演示的完整 demo）。 最终目标：以下形态全部达成。coding agent 应据此形成自己的实现方案。

    形态 A：门控的产出是「可交付的合规报告」¶

    应该成为的样子： - 门控跑完，产出的不是"通过/不通过"，而是客户可直接使用/交付的报告 - 报告要让非技术客户看懂三件事：哪条不达标 / 为什么不达标（依据）/ 怎么改 - 报告可以直接交给第三方（客户方、监管方、上级）而不需要额外解释 - 报告能体现"达标度"而不仅是"过没过"（客户要看趋势和改进）

    形态 B：标准与实现分离¶

    应该成为的样子： - 标准是可配置的数据，不是写死在代码里的逻辑 - 换一个客户 / 换一个行业，改的是配置，不是代码 - 引擎是通用的——同一套引擎服务所有客户，差异全部在标准层 - 标准能表达"为什么"（依据）和"怎么改"（修复指引），而不只是"规则本身"

    形态 C：能连续无人值守运行¶

    应该成为的样子： - 从"能跑一次"到"能连续跑、出错能定位、中途失败能断点恢复" - 任一环节失败不影响其他环节（隔离性） - 有客观证据表明它能长时间稳定运行（而不是"理论上应该稳定"）

    形态 D：客户能找到我们¶

    应该成为的样子： - 有可被搜索发现的内容资产（目标客户会搜的问题，我们能回答） - 有多语言分发能力（这是我们的独有优势） - 落地页能让人一句话说清我们做什么（不是"AI 内容工具"）

    形态 E：有可展示的信任凭证¶

    应该成为的样子： - 有前后对比案例——同一篇内容，用系统前后的差异可量化展示 - 案例既是销售证据，也是"可交付报告"的自然延伸

    三·补、本次 demo 的范围界定（2026-09-15 补充）¶

    背景：coding agent 核对代码后提出三个范围疑问。以下为发起人侧的界定，优先于任何更宽的解读。

    界定 1：「合规/标准」= 通用内容质量（本次 demo）¶

    本次 demo 采用现有门控所代表的通用内容质量标准，不实现「客户/行业自定义规则集」。

    • 第一章已定首个成果 = 采集端与生产端真跑通；第三章形态 A–E 明确标注为"最终目标：全部达成"，是终局图景，不是首个 demo 的验收项
    • 因此不存在"二选一"的冲突，这是排序问题：形态 B 的触发条件是「出现第二个客户 / 换行业」——那时才有真实差异需要表达。在拿到第一个真实客户前设计规则集，属于猜测性设计
    • 亦不触及红线：现有门控不阻碍"demo 跑通"这一目标，不落入"阻碍赚钱"三条判据 → 本次不改动现有门控

    现状事实（供核对，非方向指引）：现有门控的检查项以函数形式写在 Gate 类内；同时代码中已存在一条「品牌配置 → 门控」的数据通路（brand_profiles.yaml → GateContext.brand_profile → 各 gate 读取，如 G3BrandCTA 读 brand_name/aliases/blocked_words/cta_principles）。不存在"行业/客户规则集"概念（无规则集加载器）；brand_profile 的 industry 字段仅作描述性上下文，不驱动任何门控判定。形态 B 是否等同于"重写架构"，由 coding agent 实跑后自行判断。

    界定 2：「采集端」= 选题发现（现有能力），不新建抓取子系统¶

    本次 demo 的采集端 = 选题发现（现有 HotCollector），不新建 RSS / 网页 / 社媒趋势抓取子系统。

    • 选题发现已是真实调用外部信源（真实外部搜索 API + 真实聚合/生成层），非 mock → 已满足"真跑通"
    • 新建抓取子系统属新能力，其价值取决于客户要什么信源 → 同界定 1，留到有客户后定
    • 待修项（内存态池子 / 落库 / 定时触发）属"让现有能力真跑通"，是 demo 范围内的修，不是新建

    现状事实（供核对，非方向指引）：

    • HotCollector.collect_all() = 关键词搜索层 + 聚合/生成层 + seed 话题 → 标题去重
    • HotCollector.ingest_file() = 文档摄取（docx/pdf/pptx/xlsx/csv/json/xml/html/epub/eml/msg）
    • PoolDB = SQLite，方法集完整（增删查改 / 评分 / 标记 / 简报挂载 / 计数）
    • PoolDB(":memory:") 出现于 mcp/tools.py 三处 → 走 MCP 路径时池子为内存态，不落盘
    • cron/jobs.yaml 定义 4 个 job 模板（含 depends_on 链）；automedia cron run <job> 有真实实现
    • 但 jobs.yaml 目前只被"校验"读取，无 scheduler 消费它定时触发 → 定时需外部调度器调用 CLI

    界定 3：视频显式排除在首个 demo 之外¶

    视频不是本次 demo 的必要部分。

    • AutoMedia 自身不含视频生产：pipelines/ 只有音频与图片两条，无视频 pipeline；视频渲染依赖外部 CLI 工具 hyperframes
    • 本机当前无该外部工具（which hyperframes 为空）→ 视频模式实际跑不了
    • 架构上视频本就是独立可选轨：文本轨门控集不含任何 V 门；视频轨 V0–V7 独立成组。且外部工具缺失时，V 门优雅降级为 skipped，不判失败

    → 因此「视频链跑不通」的准确表述是「外部渲染依赖未就绪」，而非 AutoMedia 核心链断裂。把视频纳入 demo，会把工作量从"验证现有链"变成"部署调试外部渲染工具"，与第一章的 demo 定位不符。首个 demo 以文本轨（+可选图片轨）为准。

    四、边界（明确不做）¶

    • ❌ 不做通用"AI 写作/生成"功能（已商品化）
    • ❌ 不增加门控数量（已有 33 个，够用；客户看不见更多门是没意义的）
    • ❌ 不增加平台适配数量（已有 11 个真实 API 自动化）
    • ❌ 不做付费端/计费系统（等有客户再设计）
    • ❌ 不为技术洁癖而重构（重构必须有商业理由——若现有设计阻碍目标形态达成，那就是商业理由）
    • ❌ 首个 demo 不含视频生产（外部渲染依赖未就绪；视频为独立可选轨，见"三·补"界定 3）
    • ❌ 首个 demo 不做客户/行业自定义规则集（现有门控即通用内容质量标准，见"三·补"界定 1）

    五、验收标准¶

    ⚠️ 本档分两档。原版本把「终局标准」与「首个 demo 标准」混列，造成口径冲突——末条"同一内核对不同客户可配"与"三·补"界定 1（本次 demo 不做规则集）直接矛盾。以下为修正版，取代原混列版本。

    五·A 首个 demo 验收标准 ← 现在按这一档验收¶

    • demo 真跑通：采集端 + 生产端实际运行

    范围以"三·补"为准：文本轨（+可选图片轨）/ 通用内容质量门控 / 采集端 = 选题发现。

    五·B 终局验收标准 ← 有客户后逐项达成；不是首个 demo 的门槛¶

    • 非技术客户能看懂报告：哪不达标、为什么、怎么改
    • 报告可作为交付物给第三方（含依据）
    • 能说清"我们为某行业提供合规流水线"（不是"我们有个工具"）
    • 同一内核对不同客户可配（定制客户 A/C 的内容），不需要改代码

    六、红线¶

    • 现有能力不得减少（33 个门控 / 20 个平台适配 / 4,580 测试函数 / Omni Triad）
    • 任何触及现有能力的改动，需满足"阻碍赚钱"判据（阻碍交付 / 阻碍获客 / 阻碍维持），且逐项批准
    • 底线：项目为赚钱服务——如果现有设计确实挡了财路，那是要面对的问题，不是要保护的资产
