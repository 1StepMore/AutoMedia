    七阶段 AI 开发流程——用 Coding Agent 交付成品的方法论¶

    提炼自 Matt Pocock《AI Coding for Real Engineers》完整课程（剔除习题与工具绑定，保留可迁移方法论）。 核心主张：开发者应该拥有自己的流程（Own Your Process）——把任何 coding agent 包进一套可控流程，人机并行交付，而不是依赖某个特定框架。

    姊妹篇：本篇讲端到端流程（从想法到交付的七阶段）。工具链层面的方法论（prompt 工程、MCP、Cursor 等）见 AI辅助编码工作流通用方法论。

    一、总览：七阶段全景¶

    ① Grilling(访谈) → ② Research(研究) → ③ Prototyping(原型)
   → ④ PRD(文档) → ⑤ Issues(拆解) → ⑥ Implementation(实现/AFK)
   → ⑦ Review(审查)

    核心思想： - 阶段 1-5 是"人在环"（想清楚做什么、怎么做）——AI 不适合在这阶段自主 - 阶段 6 可以完全 AFK（away from keyboard，无人值守）——这是人机并行收益最大的一步 - 阶段 7 是质量闭环（验收 + 复盘 + 更新流程资产）

    ⚠️ 非线性：这不是一条死板的流水线——顺序可以灵活调整。Grilling 中途可以停下来做研究/原型，再回来继续盘问；原型结果可能反哺 PRD。课程原话："you are totally free to do these in a different order"（你可以自由地用不同顺序走完这些阶段）。阶段是心智模型，不是步骤清单。

    为什么是这套流程：当前代 coding agent 的能力边界是"执行"很强、"规划/架构判断"弱。这套流程把需要人类判断的部分前置（grilling/PRD），把可以自动化的部分交给 agent（implementation），并在末尾强制验收（review）。

    二、各阶段详解¶

    阶段 1：Grilling（访谈/盘问）¶

    目的：用 agent 拷问想法，把模糊概念硬化成可执行的方向。

    要点： - 把 agent 当"挑剔的产品评审"：让它从用户、技术、商业多个角度盘问你的想法 - 期望产出：对想法的强弱点清单、需要进一步研究的问题列表 - 这是一个对话式迭代过程，不是一次性问答

    可操作性： 1. 给 agent 一个模糊想法 2. 让它列出 5-10 个"这个想法会被质疑的点" 3. 逐轮回答，直到没有新的质疑 4. 把过程中产生的决策记录成 ADR（架构决策记录）

    阶段 2：Research（研究）¶

    目的：解答 grilling 阶段提出的开放问题。

    触发条件：当 grilling 中暴露出"不确定"的点——第三方 API 能力、工具选型、技术路线、市场上有无现成方案。

    要点： - 研究结果是决策输入，不是文档任务 - 通常伴随小型验证（能否调通某 API、某库是否满足需求） - 研究可能中断 grilling，也可能穿插在 prototyping 中

    阶段 3：Prototyping（原型）¶

    目的：用最小实现验证关键技术假设。

    要点： - 针对研究阶段的不确定点，快速写"能跑通的最小演示" - 原型可能被复用，也可能被丢弃——目的只是降低不确定性 - 原型 ≠ 正式实现：不追求架构、不做完整错误处理

    常见分支： - 交互式原型：验证用户体验/交互路径 - 技术原型：验证数据模型、API 集成、性能假设

    阶段 4：PRD（产品需求文档）¶

    目的：把"去哪里"写清楚，作为团队可审查的目的地文档。

    要点： - PRD 是后续所有 issue 的唯一事实来源 - 必须包含：用户故事/需求、验收标准、范围边界 - 写入代码库（如 docs/），让 agent 可直接访问

    进阶（模块意识）：写 PRD 时预先规划要构建/修改的主要模块——主动寻找可隔离测试的"深模块"机会（见 Deep Modules 方法论）。在文档中画出模块草图并和用户确认。

    阶段 5：Issues（任务拆解）¶

    目的：把 PRD 翻译成带依赖关系的可执行任务。

    要点： - 每个 issue 应该是可独立完成的原子任务 - 用阻塞关系（blocking links）表达任务间依赖 - 拆解粒度：一个 issue 对应一次可验证的提交 - 可直接落到 Kanban 板管理

    阶段 6：Implementation（实现）——AFK 模式¶

    目的：让 agent 自主完成编码，人类去做别的事。

    两种模式： | 模式 | 说明 | 适用 | |------|------|------| | 人在环 | 看着 agent 做，随时干预 | 高风险/需要频繁判断的任务 | | AFK（无人值守） | agent 按 issue 列表自主完成 | 目标明确、依赖清晰的批次 |

    AFK 的关键前提（不满足就不要 AFK）： 1. PRD 和 issue 足够清晰（否则 agent 会自由发挥） 2. 代码库有测试反馈循环（agent 犯错能被测试捕获） 3. 模块边界已定义（agent 不容易破坏其他部分）

    收益：人类规划下一批工作时，agent 同时在交付当前批次——并行化是这套系统的核心价值。

    阶段 7：Review（审查）¶

    目的：验证"到达了目的地"，并复盘改进流程。

    双层审查： 1. 结果审查：对照 PRD 逐项验收——是否所有需求都实现了？ 2. 过程审查：哪些 prompt 需要更新？哪些 skill 需要调整？把过程改进沉淀回流程资产（prompt/skill 库）

    关键：review 不是终点，而是流程复合增长的起点——每轮都让下一轮更快。

    三、关键方法论支撑¶

    3.1 Deep Modules（深模块）：为 AI 优化代码库¶

    来源：《Philosophy of Software Design》（John Ousterhout）

    底层动机：AI 时代人类的认知负担在上升。使用 AI 编码后，agent 频繁改动代码，你在脑中维护的"代码内部地图"不断失效——这是所有重度 AI 用户的共同体验。任何能降低认知负担的策略，都能直接改善你的 AI 工作体验。深模块正是这样的策略：你只需记住接口，不必维护实现细节的地图。

    定义：小接口 + 大实现的模块。接口是薄薄一层公开 API，背后封装大量实现。

    为什么对 AI 重要： - AI 无法像人一样"记住"代码库全貌——每次都要重建关系图 - 深模块让 AI 只读接口就能理解模块职责，快速导航整个代码库 - 浅模块（接口和实现一样复杂）会让 AI 在 import-export 链里迷路

    对人类的额外收益： - 降低认知负担：你只需记住接口，不用维护内部地图 - AI 改代码时不容易弄坏结构：实现藏在接口后，测试锁住行为 - 你主要读测试而不是读实现（灰盒视角）

    如何落地： - 重构时：找"小而散、彼此耦合"的模块群 → 合并为深模块 - 写新功能时：在 PRD 阶段就规划模块形状，主动找深模块机会 - 测试策略：对深模块写集成测试（测整个模块的对外行为），而不是逐个浅模块单测

    ⚠️ 陷阱：AI 的"为可测试性提取"往往是坏重构。课程实测观察：LLM 很爱说"把这块抽出来让它可测"，然后抽出一个纯函数——但真正的 bug 往往出在调用方式上（前端怎么调后端、后端怎么调 CLI）。为了可测试性提取小函数，接口和实现一样复杂（浅模块），测试锁住的只是形状而不是行为。识别标准：如果抽出后你还是要写一堆 mock 才能测，说明抽错了——应该往"把整个流程包成一个大服务"的方向走。

    完整实操：5 步改进代码库架构（Improved Code Base Architecture） 

    1. 探索（找摩擦点）——让 agent 用 explore 模式通读代码库，记录：
   - 理解一个概念要跳几个小文件？
   - 哪些模块接口和实现一样复杂（浅模块）？
   - 哪些纯函数被抽出"为了可测"，但 bug 出在调用处？
   - 哪些紧耦合模块之间存在集成风险？
2. 列候选——不设计接口，只圈出"共享概念、彼此耦合"的模块群
3. 用户选一个候选
4. 并行设计接口——多个 subagent 同时产出**差异最大化**的接口方案
   （多样性最重要，后期可混合）
5. 推荐/混合 → 生成重构 RFC（GitHub issue）→ 转 Kanban 拆解
    用法：日常可以带定向（"看看这个模块区域"），也可以全库扫描。这是预防与治疗：改进流程是"治疗"（修已有坏模块），而 PRD 阶段的模块意识是"预防"（新代码从源头就是深模块）。

    3.2 Grill with Docs：解决 AI 回答不了的两个问题¶

    AI 只靠代码+commit 历史+GitHub+用户消息，回答不了两个关键问题： 1. "为什么这样做？"（代码里的奇怪取舍） 2. "XXX 是什么？"（业务行话）

    解法： - ADR（架构决策记录）：把重要决策写成小 markdown 文件放代码库——为什么做这个选择、考虑过哪些替代方案。AI 可直接读取 - 共享术语表（context.md）：把业务行话定义成代码库根目录的 glossary。AI 不需要你重复解释 - 创建时机：最早越好——grilling 阶段就要建立，先于 PRD（否则后续 issue 会沿用旧术语）

    来源思想：Domain-Driven Design 的 Ubiquitous Language（通用语言）——术语表不仅帮助人机对话，也让变量命名、代码搜索更一致。

    3.3 AX（Agent Experience）优先：Greenfield 项目的第一 PRD¶

    概念： - UX = User Experience（终端用户体验） - AX = Agent Experience（agent 在代码库里的工作体验）

    关键判断：Greenfield（全新项目）的第一份 PRD，应该先定义 AX 而不是 UX。

    AX 要定义的四件事： 1. 反馈循环：测试类型、pre-commit hooks、格式化——确保 agent 犯错能被自动捕获 2. 技术选型：语言、框架（难以更换，必须 grill 确认） 3. 模块形状：初始深模块设计（代码库架构 = agent 体验） 4. 测试策略：mock 什么、是否用测试数据库

    原因：技术选型和模块形状一旦定了很难改；如果一开始就让 agent 在烂结构里工作，后续所有迭代都吃亏。UX 可以后续优化，AX 必须起步就设计。

    四、快速上手清单（30 天可落地）¶

    周 动作
    1 选定一个 coding agent（CLI 类）；跑通最小工作流（一个 issue 从拆解到 AFK 实现）
    2 建 docs/ 结构：context.md 术语表 + ADR 目录；对现有代码库跑一次"深模块体检"
    3 用完整七阶段跑一个真实小功能：grilling → PRD → issues → AFK → review
    4 复盘：更新 prompt/skill 库；把 review 中发现的流程改进沉淀为 skill

    五、适用边界（诚实评估）¶

    这套方法论适合： - 有明确需求的软件项目（web app、工具、库） - 团队或个人已经熟悉 coding agent 基础操作 - 代码库已具备基本测试能力（AFK 的前提）

    不适合/需要调整： - 纯探索性项目（需求无法前置明确）——grilling/PRD 阶段会显得过重 - 代码库完全没有测试——必须先补测试反馈循环，否则 AFK 会失控 - 一次性脚本/小工具——七阶段是过度工程，直接让 agent 写更快

    关键认知：这套流程的价值在中大型、需长期维护的项目。小任务用全流程是浪费。
